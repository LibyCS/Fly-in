**Description**
A multi-agent drone pathfinding program on a grid, which uses A* search, reverse Breadth-First Search algorithms and reservation tables to sechedule all drones and keep track of them so that they all obey node capacities, conection capacities and zone rules as listed by the map text files.
The project also includes visualisation of the map and the drones as the drones traverse the map, based off their paths calculated by the A* search algorithm, generated by matplotlib to be viewed as a png that updates every half a second.

**Algorithm**
A* Search (Modified) - Based off the A* search algorithm with the added turn order, so the open queue list has both the node and turn, this is referred as the node state. Our program has to account for restricted zones, blocked zones, priority zones capacity limits and connection limits.
Each path calculated using A* Search had to refer to the reserbation table to check capacity limits at each node at a certain turn to make sure all rules are obeyed.

How A* search works:
(Nodestate is a class that contains the associated node and turn)
1. Starting with the start node, compute the start nodestate and add start Nodestate to the open queue.
2. Find the best nodestate in the open queue through their f, h and g values and set it as the parent.
3. Compute the children's f, g and h values and create their nodestates.
f value is the g and h values added together.
g value is the path cost needed to get to the current node from start.
h value is the path cost needed to get to the goal from the current node, calculated using reverse breadth-search.
4. Add the parents's children Nodestate, by com to the open queue with their associated turn (parent turn + 1 (+ 1 if restiricted)), unless the child node is already in open or closed queue and the f, g, h values are better.
5. Parent Nodestate is added to the closed node and removed from the open queue.
6. Update the parent dictionary by associating the child nodestate as the key and the value is the parent's nodestate.
7. steps 2 to 6 are repeated till the search for the best nodestate chooses goal as the best node to move to.

Why A* Search was chosen:
The algorithm is able to efficiently choose lower cost path between start and goal while accounting for heuristics (f, g and h) to decide which node would be the lower cost. Compared to Dijkstra's and Breadth-First Search it seeks out the best node to check first so therefore looks at less nodes compared to the other two. It also made it easier to incorporate a reservation table as well as adding extra weight to the g/h values if say the node wanted to traverse to a restricted zone.

Reverese Breadth-First Search - Like Breadth-First Search but instead of staring from the start you start from the goal and make your way backwards.
This makes it easier to calculate the herustics for h, to estimate how many hops would be needed to get from the current node to goal.

How Reverse Breadth-First Search works:
1. Create an empty hops dictionary which accepts a node and equals to the number hops it took to get from the goal to that node.
2. Add goal to the queue and add goal to the hops dict setting it to 0.
3. Take the first element in the q and set it as the parent. 
4. Add the children to the queue if the child node cannot be found in the hops dictionary's keys.
5. Add each child to the hops dictioanry equal to the hops[parent] + parent_zone weight which is determined by the type of zone the parent has, i.e resticted zone weighs 2 while normal zone weighs 1. 
6. Repeat Steps 3 to 5 till the queue is empty.

Why Reverse Breadth-First Search was chosen:
I needed to make a quick table to give a best estimate on how far one node was from goal, instead of doing a breadth-first search where I would need to start the counter once it found the node it was easier to start from goal where everything is proportional from where the goal was. Reverse Breadth-First Search is also quick to implement and doesnt care for weather their is any capcity limits, its just to give a rough estimate on the h value, it was also easy to add cost to the path cost from goal to whatever node is reached.

**Data Structures**
Reservation table - Also known as the timeline in my program, it stores all the drones pathways that have so far been calculated using A* search and thier associated turns. This allows the program to look up a node at a certain turn to check if capacity limit has been exceeded. Also used in the turn generator to get all drones placement during each turn to be visualised. It is converted into a dictionary of node and connect reserves to make it easier to look up capacity during a* search.

Open queue - The queue that stores the viable nodestates to go check.


Closed Queue - The queue that holds all the nodestates that have been checked to make sure they arent rechecked.

Input and Output:
Please run the command to run the program:
make run FILE=<map.txt> - where map.txt is the text file, if the text file is not in the root then make sure to add the pathway too.
To view the visualiser you must immediately click on the newly created visualiser.png that appears in vscode. This may not work if you do not have automatic refresh when a file is updated.

The map.txt file itself will follow the format as shown below:
# Easy Level 1: Simple linear path
nb_drones: 2

start_hub: start 0 0 [color=green]
hub: waypoint1 1 0 [color=blue]
hub: waypoint2 2 0 [color=blue]
end_hub: goal 3 0 [color=red]

connection: start-waypoint1
connection: waypoint1-waypoint2
connection: waypoint2-goal

- nb_drones must be the first actual line that is parsed through, if a hub is initilaised before it then the program fails.
- Hubs must be of type start_hub, hub or end_hub.
- All hub names must be unique and connot contain a "-" in its name.
- Connections must be between hubs that have already been validated from the lines above
- Accepted Metadata for hubs are zone, color, and max_drones. A hub can have up to 3 unique metadata tags seperated by spaces.
- Accepted Metadata for connections is max_link_capacity only formated the same was as hub metadata.
- There must be a start hub and an end hub, their capacities are considered infinite even if specified.

Output example:
D1-waypoint1 D2-waypoint1 
D1-waypoint2 D2-waypoint2 
D1-goal D2-goal

Each line represents a turn passed, with the drone shown as D and its associated number, so D1 represents Drone 1.
The drone is followed by the hub name which shows that in this turn the drone has moved to the specified hub.
If the drone waits its turn or has reached the goal it will not be displayed in the output as it does not move.
